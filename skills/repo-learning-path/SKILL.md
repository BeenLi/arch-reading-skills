# 仓库学习路线与精读笔记

目标：让读者从自己现有的背景出发，一步步把一个仓库真正读懂。产出是仓库里的一组文档：

```
<docs>/learning/
├── README.md                 学习计划与索引：背景、目标、分阶段路线、每阶段的精读待办
├── 00-0-<主题>-overview.md    每个大阶段一篇总览：只放地图（架构图、分篇表、待核实清单）
├── 00-1-<主题>.md             精读分篇：一项一篇
├── 01-0-...
└── figs/
    ├── README.md             每张图的来源
    ├── official/             官方或互联网上现成的图（下载来的）
    └── drawn/                自己画的图
```

`<docs>` 用仓库已有的文档目录（`docs/` 或 `Docs/`），没有就建 `docs/`。文档语言跟用户说话的语言一致。

和 repo-reader 的分工：repo-reader 一次写出一份固定 12 节的"架构和使用文档"；本 skill 是按读者背景排的多阶段学习路线，加上逐篇精读，每一步都和用户确认。用户只想快速知道"这个仓库是什么、怎么用"时，用 repo-reader。

## 依赖检查

本 skill 自身只需要 Python 3。画图时用到两个可选的 skill，第一次要自己画图时检查：

```bash
ls -d "${DRAWIO_SKILL_DIR:-$HOME/.claude/skills/drawio-skill}/scripts" "${VERILOG_DIAGRAM_DIR:-$HOME/.claude/skills/verilog-diagram}/scripts"
```

- **drawio-skill 缺失**：一般软件的架构图、时序图画不了，drawio 图的 `validate.py` 也跑不了。把安装命令告诉用户：`npx skills add Agents365-ai/drawio-skill -g -a claude-code -y`，用户同意后才代为执行。
- **verilog-diagram 缺失**（它和本 skill 在同一个仓库 arch-reading-skills 里）：硬件结构图画不了。告诉用户：`npx skills add BeenLi/arch-reading-skills -g -a claude-code`，同样等用户同意。
- 用户不装时改用手写 SVG 或 Mermaid 代码块，并在汇报里说明退回到了哪种画法。不影响找现成的图和写文字。

## 为什么要分关、每关都停下来

学习路线好不好，取决于它和读者的背景、目标是否匹配，这只有读者自己能判断。一次性生成"路线 + 大纲 + 全部笔记"看似高效，实际上前面任何一步跟读者对不上，后面全部白写。所以每一关结束时**把结果交给用户，明确提出要确认的问题，然后停下等回答**，不要在同一轮里替用户回答、接着写下一关。用户说"可以/没问题"才算共识；用户提出修改，就改完再确认一次。

## 第零步：先判断从哪一关开始

- 先看 `<docs>/learning/README.md` 在不在。如果在，读它和各篇总览，找到第一个没打勾的精读项，告诉用户"上次进行到哪里、下一篇是什么"，从第四关或第三关接着做，不要重建路线。
- 用户在请求里已经给出背景和目标，就不用再从头问，把没说到的部分补问即可。
- 用户已经认可了一份路线（例如贴了出来），就直接进第三关。

## 第一关：了解仓库，再问背景和目标

先花几分钟只读地勘察仓库，再提问，这样问题才具体：读 README、目录结构、主要语言、代码规模（`git ls-files | wc -l`、按目录统计行数）、构建/测试入口、仓库自带的文档和图（`docs/`、`images/`、wiki 链接）。不要在这一步精读代码。

然后用两三句话告诉用户"这个仓库大概由哪几块组成"，再问：

1. **背景**：相关领域懂多少（结合勘察结果具体问，例如"Verilog 读得懂吗？GPU 的 SIMT 概念熟吗？"而不是"你的背景是什么"）；平时用什么语言；有没有读过类似项目。
2. **目标**：读完想能做到什么——会用、能改、能贡献、能和另一个实现对照、准备面试，还是只要理解设计思想。目标决定路线的终点和每篇笔记要回答的问题。
3. **约束与偏好**：大概投入多少时间；有没有参考书或课程想对照（它决定 🆕 标记的参照物，见模板）；有没有特别想先看或不想看的部分。

能用选择题提问工具就用（选项写成从勘察结果推出来的具体选项），否则直接列问题。问完就停。

## 第二关：定学习路线（在对话里，先不写文件）

根据背景和目标，把学习路线分成若干**大阶段**，从 00 或 01 开始编号。每个阶段写：

- 目标：读完这一阶段能回答什么问题、能做什么。
- 为什么放在这个位置：它依赖前面哪一阶段，又为后面哪一阶段铺路。
- 大致范围：涉及哪些目录或模块（用仓库里的真实路径）。
- 粒度：预计拆成几篇精读。

排路线的原则：

- **从读者已经会的地方切入**，第一阶段要让读者很快获得一个完整的全貌（比如跑通一个例子、看懂顶层数据流），不要一上来就钻进最难的模块。
- **每一阶段只引入一类新东西**。读者的薄弱点要拆细，熟悉的部分可以合并或快速带过。
- **先建方法论或全貌，再读细节，最后做综合**（对照、改动、实验）。如果有多个阶段都要用到的读法，可以单列成第零步，就像先学"这两套代码各自的写法"再去读具体部件。
- 路线的终点对准用户的目标。

把路线交给用户时，明确问这三个问题，然后停下：

- 哪一步迈得太大，需要拆开或加一个铺垫阶段？
- 哪一部分对你来说太简单，可以跳过或合并？
- 还想加入哪些这里没有的内容？

## 第三关：把路线落成 README 大纲

路线达成共识后，按 [references/templates.md](references/templates.md) 写文件：

1. `README.md`：背景与目标（用户的原话要点）、路线总表、每个阶段一节，节内是该阶段的精读待办（`- [ ]`）。**最近一个未完成的阶段**要拆到"一篇笔记一项"，每项写清：要读的代码入口（带行号的相对链接，链接前先确认文件和行号存在）、这一篇要回答的问题。后面的阶段只写到粗粒度条目，开始那个阶段时再细化——现在细化会过早固定还没摸清的东西。
2. 每个阶段一篇总览 `NN-0-<主题>-overview.md`：只搭框架，标题、开头引用块、"（待写）"占位和空的分篇表。
3. `figs/README.md`（先写一句说明即可）。
4. 如果仓库有 `CLAUDE.md` 或 `AGENTS.md`，问用户要不要把文档约定（命名、标记、链接、图的规则）写进去，以后的会话就能自动遵守。

写完后，只请用户确认**最近一个未完成阶段**的细分篇目：篇目划分、顺序、每篇要回答的问题是否合适。后面阶段的内容不用确认。然后停下。

## 第四关：问是否开始写第一篇

大纲确认后，问用户"要不要现在写第一篇精读：《NN-M 标题》？"，等回答。用户同意了再写。

## 写精读文档

格式见 [references/templates.md](references/templates.md) 的"精读分篇"。要点和理由：

- **先读代码，再写结论。** 每一条事实都要能落到具体的 `文件:行号`；读到的直接标 ✅，推测的标 ❓。宁可多一个 ❓，也不要把推测写成事实，因为读者会照着笔记去理解代码。
- **结论要具体。** 不写"这个模块负责调度"这种泛泛的话，要写成"第几拍 / 哪个函数 / 哪个变量 / 哪个参数"这一级的结论。对照两个实现时，先讲一边、再讲另一边、最后对照。精读结论单独成节，标题写成"精读结论（YYYY-MM-DD）：一句话结论"。
- **代码引用一律是相对本文件的链接并带行号**，例如 `[`core.sv:42`](../../src/core.sv#L42)`，范围写 `#L42-L50`。VS Code 和 GitHub 上都能点击跳转。短摘录代码可以放进代码块，但旁边要有链接。
- **每篇至少一张图，图文配合**：放在相关段落旁边，图前或图后用一两句话告诉读者"看图里哪几处"。找图的顺序：
  1. 仓库自带的图（`docs/`、`images/`）直接用相对路径引用，不复制。
  2. 官方文档站、论文或成熟博客里的图：下载到 `figs/official/`，在 `figs/README.md` 写明来源链接。下载前确认是那个项目或版本的图，不要拿名字相近的别的项目的图。
  3. 都没有时自己画，放 `figs/drawn/`：硬件/RTL 结构优先用 verilog-diagram skill（`.yaml`、`.drawio`、`.png` 三件，yaml 头部注释写清依据的代码行）；一般软件架构、时序、流程用 drawio-skill；位域、指针位置这类结构图可以手写 SVG；都不可用时用 Mermaid 代码块。画完渲染出 PNG 并**亲自打开看一遍**（拥挤、重叠、文字截断都要修），drawio 图跑 validate 要求 0 error。在 `figs/README.md` 记一行。
- 写完运行链接检查，修好所有报错。在本 skill 目录下运行（`<docs>` 写绝对路径）：

  ```bash
  python3 scripts/check_links.py <docs>/learning/
  ```

- **同步索引**：README 里该项打勾，括号里写日期和笔记链接；总览的分篇表填上这一篇和一句话结论；总览待核实清单里被这篇解决的 ❓ 改成 ✅ 并写结论。新发现的问题加进待核实清单或后面的待办。

写完一篇后，用两三句话告诉用户这篇的结论，问是否接着写下一篇（说出下一篇的标题）。如果读的过程中发现大纲需要调整（某项该拆开、某项其实不存在），先说明并请用户确认，再改 README。

## 编号与命名

- 阶段号两位数 `NN`；总览 `NN-0-<英文主题>-overview.md`；分篇 `NN-M-<英文主题>.md`，`M` 从 1 起。主题用小写英文加短横线。
- 内容紧密相关的可以合成一篇。改编号或合并时，同步改 README、总览和其他分篇里的链接（改完再跑一次链接检查）。
- 标记：✅ 从代码或配置直接读出；❓ 待核实；🆕 超出读者已有知识（或所选参考书）的新东西。三个标记的含义在每篇开头的引用块里说明。
