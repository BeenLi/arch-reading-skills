# 科普 / 调研文档

把一个"大家都在用、但说法很乱"的主题，梳理成一份读完就能建立坐标系的中文文档。样板是《计算机体系结构建模方法学梳理》：它不按工具罗列，而是先拆出几个独立维度，把每个工具放进坐标系，再讲每个工具"原本是为谁、站在哪一层设计的"，最后讲它们怎么组合（联合仿真）。

适用领域：计算机 / 集成电路 / 大模型基础设施、金融投资、也可以是生活话题。读者是聪明的外行或相邻领域的工程师。

## 0. 输入与范围

先确认（用户没说就按默认推断，并在私人文档里注明你对范围的理解）：

- 主题，以及用户心里"混乱的那组概念"是什么（例：functional / cycle-level / cycle-accurate / RTL）。
- 用户给的资料（链接、PDF、图片、自己的笔记）。逐一读完。若某份资料和主题对不上，写进私人文档（见下），公开文档里不提"你给的资料"。
- 用户自己的研究/工作场景（如果知道）：只写进私人文档，不进公开文档。
- 输出位置：默认 `<topic-slug>/` 目录，内含：
  - `<主题>.md` + `<主题>.pdf`：**公开文档**，要发到互联网上。Markdown 是源文件，**每次都要交付**，PDF 由它导出；用户会在 md 上批注，再让 Agent 照批注修改；
  - `<主题>_宣传简介.md`：**宣传简介**，独立于正文的一份短文案（≤500 字，顶部放封面图），发布时配在文档旁边（见第 11 节）；
  - `figs/cover/`：封面 `cover.json` → `cover.html` → `cover.png`（见第 10 节）；
  - `figs/`（网图）、`figs/drawn/`（自绘图 + 生成脚本）；
  - `<主题>_个人映射.md`：**私人文档**，只给用户自己看，不发布。

## 隐私边界（公开 vs 私人）

公开文档面向陌生读者，写成通用科普，**不能出现任何能把文章和用户本人当前研究联系起来的信息**：
- 不写用户的研究课题、在做的项目/仓库名、所在单位、导师/同事、未发表的想法和数据；
- 不用"你的 Cmodel""你的工作流""你定下的做法"这类第二人称指向用户本人；需要举例就用通用的"如果你在做 X"或第三人称的公开案例；
- 文首注释、图注、文件路径、脚本注释、PDF 元数据里也不能带这些信息（例：不出现 `/Users/<用户名>/`、私有仓库名）。

私人文档 `<主题>_个人映射.md` 承接被移出的内容，结构：
1. 用户给的资料说明与纠偏（哪份资料对应公开文档哪一节、哪份不对题）；
2. 用户当前研究/工作在本文坐标系里的位置（可用表：你的做法 | 坐标 | 回答的问题）；
3. 缺的那一环，以及业界通常怎么补；
4. 下一步值得想的问题。
私人文档可以引用公开文档的小节号和图号，不必重复正文。

## 1. 调研

- 一手来源优先：原论文、官方文档、项目 README、标准手册。二手文章只用来找线索。
- 每个关键数字（速度、误差、占比、收益率）都带出处和年份；量级数字注明"各来源不同平台，仅作定性比较"。
- 搜索时专门找：该领域经典综述里的那张"分类图"、各对象自己的论文/官网怎么描述自己、独立第三方评测（专门找它们指出的边界和反例）。
- 记下可直接引用的网图 URL（论文图、官方架构图、logo），后面要用。

## 2. 先找"坐标轴"，再写正文

动笔前回答三个问题，答案就是文章骨架：

1. **大家用一个词描述的东西，实际混了几个独立维度？** 目标是拆出 3–5 条正交的轴，每条轴写成"问的问题 + 取值举例"。
2. **每个对象在每条轴上取什么值？** 能放进同一张图里，才算梳理清楚。偏离"对角线"的那几个点最有说服力，重点讲。
3. **每个对象原本是为谁、为解决什么问题造的？** "精度/好坏"只在它站的那一层有意义。

用户偏爱"特别的角度、事物原本工作的样子"，所以每节都要追问：它底层到底怎么运转（例：时间 t 怎么变成 t+Δ）、设计者当初的约束是什么、常见说法哪里不对。

## 3. 文章结构（按需裁剪，保持顺序）

```
# <主题>梳理
> 调研日期 / 目标（一句话，把哪些东西放进一个统一坐标系）
> 图的来源说明（网图出处、自绘图脚本位置）

## 0. 一句话结论        ← 先给结论，加粗核心论断 + 维度表（维度 | 问的问题 | 取值举例）+ 总览图
## 术语速查              ← 紧跟结论、在正文之前：两列表（术语 | 一句话定义），收录正文会用到的所有缩写和行话，按"先基础后进阶"排序；英文缩写后面括号写出英文全称，如"DPU（Data Processing Unit）"
## 1. 为什么会混乱       ← 被混用的词表（词 | 字面含义 | 实际在说哪个维度）+ 一句"关键区别"
## 2..N. 坐标系一/二/三  ← 每节一条轴：经典图/自绘图 → 点位表 → 用它读具体对象的表
## N+1. 逐个对象：它们各自"原本是干什么的"  ← 站位图 + 每个对象一小节，标题写成"X：___视角的___"
## N+2. 组合使用 / 联合仿真  ← 本质是哪两件事要对齐；分类图；Amdahl 式的瓶颈推论
（不设"对你的场景的映射"一节，这部分只进私人文档）
## 参考                  ← 作者, 标题, 会议/年份, 链接
> 数字口径说明
```

金融或人生话题同理换皮："维度"可以是风险来源 / 期限 / 流动性 / 谁是对手方；"原本是干什么的"是某个工具或制度诞生时要解决的问题；"组合使用"是对冲、配置或决策搭配。

## 4. 写作规范

- 中文为主，术语首次出现保留英文原词。正文出现的缩写/行话都要在前置的"术语速查"里有一行，读者先查表再读正文。术语速查里每个英文缩写都紧跟英文全称（缩写（Full English Name）），再给中文一句话定义；非缩写术语不用。
- 每节第一句就是这节的结论，粗体只用在论断上，一节不超过一两处。
- 用"混乱的第一个来源 / 第二个来源"这类钩子把前后串起来。
- 纠正常见说法时给出"更精确的说法"，并指到具体小节。
- 举例用具体数字和具体对象，不说"某些工具"。
- 段落短，3–5 行；列表项写成完整句子。
- 不写空话开场、不写总结性客套。

## 5. 图（必须有，且每张都要有信息量）

全文至少 4–6 张图：一张**总览坐标图**（所有对象放进主坐标系）是硬性要求，其余放在"需要空间想象"的地方：机制对比、量级阶梯、层级/分形结构、站位图、组合方式示意。

**网图**：经典论文图、官方架构图、logo。
- 下载到 `figs/`，正文用相对路径引用，不要热链。
- 图注写明出处（作者/项目 + 链接），logo 来源统一记到 `figs/logos/README.md`。
- 先确认图能下载、内容就是你要的那张；拿不到就自己画。

**自绘图**：结构/流程/层级示意图优先用 diagram-design（HTML/SVG → 2x PNG），按第 10 节的固定风格；数据图（散点、量级阶梯、柱状）用 Python matplotlib 生成 2x PNG，配色同样取第 10 节的色板。mermaid 只作草稿，导出前要渲染成图片。
- 生成脚本放 `figs/drawn/make_figs.py`，文首写一行如何重生成。
- 中文字体显式指定（Noto Sans CJK SC / PingFang SC / Source Han Sans），检查没有方块字。
- 用形状 + 颜色编码额外维度，并画图例；对象名直接标在点旁边，避免只靠图例对照。
- 画布紧凑：`bbox_inches='tight', pad_inches=0.05`，不留大白边；宽度按正文栏宽设计，字号在缩放后不小于正文的 70%。
- 画完自己打开看一遍：标签有没有重叠、出界、被截断。

**图注**（每张图下方，斜体一段）：`图 N：<这张图说明了什么>。<最值得看的那个点/反例>。` 图注说洞见，不复述图里的文字。

## 6. 表格（要精、要齐、要紧凑）

- 每张表 2–5 列。超过 5 列就拆表，或把次要信息挪到正文。
- 第一列是"对象/维度名"，短；最后一列放长说明。单元格尽量一句话，不超过 ~40 字。
- 同一列的取值用统一词表（例：untimed / approx / cycle），方便竖着比。
- 表前一句话说这张表要读出什么，表后不再重复表的内容。
- 数字列右对齐、量级用上标写法（10² – 10³），单位写在表头。
- 不要在单元格里换行堆列表；需要列表就不是表。

## 8. 按批注修订

用户把批注过的 md 发回来时（形式可能是 `<!-- 批注 -->`、`> 批注：…`、`==高亮==`、行内括号或单独的批注清单）：
- 以 md 为唯一源文件，逐条处理批注，改完删掉批注标记；
- 批注涉及图就改 `make_figs.py` 重新生成，不要手改 PNG；
- 改完重新导出 PDF，再过一遍第 12 节自查（尤其隐私和空白）；
- 正文改动影响到宣传简介或封面（新增/删除小节、数字变化）时同步更新简介和 `cover.json`，重出封面；
- 回复里用几行列出每条批注怎么处理的，有没采纳的说明原因。

## 9. 标题推荐（正文写完后、做封面前）

用户只定了主题，最终标题要贴合写出来的内容。正文定稿后，给用户推荐 **3–5 个候选标题**，每个配一句理由，并标出你推荐的那个：

- 角度各不相同，例如：直述型（"DPU 的来由与软硬件架构"）、反常识问题型（"网卡为什么长出了 CPU？"）、"原本是干什么的"型（"一块网卡，怎样长成另一台计算机"）、数字/历史型（"I/O 第三次被搬出 CPU"）。
- 每个都要对得上正文真正讲了什么，不标题党；不用正文没覆盖的概念。
- 同时给出配套副标题，并满足封面限制：主标题 1–2 行、每行 ≤7 个汉字，副标题 1–2 行、每行 ≤12 个汉字。
- 用选择卡片（若可用）或编号列表交给用户；用户没回复前先按推荐项往下做，选定后统一替换。

用户选定后，同步到所有地方：md 的一级标题、PDF、`cover.json` 的 title/subtitle、宣传简介标题、文件名（`<主题>` 部分）、私人文档里的引用。

## 10. 封面图与固定视觉风格

每份文档都要一张封面，风格固定，**换主题只换内容和母题，不换版式**。母题有同心圆（rings，默认）、台阶（stairs）、时间轴（timeline）三种，按主题的形状选（见 `COVER-STYLE.md`“母题”一节），不要硬套同心圆。规范和生成器都在本 skill 目录里：`references/COVER-STYLE.md`（规范）、`scripts/make_cover.py`（cover.json → cover.html）、`scripts/export_cover.py`（HTML → PNG），样板是 `assets/cover-example/cover.png` 和同目录的 `cover.json`。开工前先读 `COVER-STYLE.md`；若与下面的摘要不一致，以该文件为准。下面的命令都在 skill 目录下运行（`~/.claude/skills/kepu-research-doc/`）。

生成：
```bash
python3 scripts/make_cover.py <topic>/figs/cover/cover.json <topic>/figs/cover
python3 scripts/export_cover.py <topic>/figs/cover/cover.html   # 1242×1656 PNG（小红书 3:4 竖版）
```
`export_cover.py` 只依赖 Playwright + Chromium（`python3 -m pip install --user playwright && python3 -m playwright install chromium`；装不上就按「视觉规定摘要」用 diagram-design 手写 `cover.html` 导出，并在回复里说明封面没用生成器）。生成后打开 PNG 自己看一遍，再做一轮美化：文字有无溢出/重叠、圈上标签是否挤、留白是否均衡，有问题改 `cover.json` 重出，不手改 PNG。

`cover.json` 字段：
| 字段 | 内容 |
|---|---|
| eyebrow | 英文大写关键词，用 · 分隔，最后一项写"科普调研" |
| title | 1–2 行，每行 ≤7 个汉字 |
| subtitle | 1–2 行，每行 ≤12 个汉字，一句话说"原本是怎么回事" |
| topics | 3–4 行"这篇要讲什么"：[英文标签, 一句话问题]，标签用 WHY / WHAT / HOW / WHO；不放图数、参考数等统计数字 |
| meta | 日期 · 页数 · 语言 |
| motif | `rings`（默认）/ `stairs` / `timeline` |
| core | rings 用：同心圆圆心的核心对象 [中文名, 英文小字] |
| rings | rings 用：2–6 圈 {year, label, sweep, dashed?, focal?}，只能一圈 focal |
| stairs | stairs 用：3–6 级 {label, sub?, layers: [自下而上], focal?}，只能一级 focal |
| timeline | timeline 用：3–7 个 {year, label, dashed?, focal?}，只能一个 focal |
| motif_caption | 母题下方一句斜体说明 |
| desc | 无障碍描述，一句话 |

视觉规定摘要：
- 画幅：**小红书封面 3:4 竖版**，画布 1080×1440，导出 ×1.15 得 1242×1656 PNG；四周留 96px 安全边距，iPhone 预览裁边或底部遮挡时不切到文字。版式自上而下：标题区（eyebrow、标题、橙色短横、副标题）→ 点阵纸上的同心圆母题（上下各一条细线）→ 3–4 行 topics → 页脚。
- 母题：rings 的圆心=核心对象，每圈=一个阶段，弧长即信息（走完约 300°，进行中约 200°，淘汰的画虚线）；stairs 从左到右是层级，块数=该级累积的东西；timeline 是一条主线上的节点。三种都只有一处焦点。横版目前只支持 rings。
- 色板（diagram-design 默认皮肤）：paper `#f5f5f5`、ink `#2d3142`、muted `#4f5d75`、soft `#5a6580`、rule `rgba(45,49,66,0.12)`、accent `#bf4520`。accent 只用两处：标题下短横条、焦点（圈、台阶或节点）。
- 字体：标题/大数字 Instrument Serif（中文回落 Noto Serif SC 700），正文 Geist + Noto Sans SC，eyebrow/年份/页脚 Geist Mono。
- 不要渐变、阴影、>6px 圆角、emoji、多于一处焦点。

正文示意图也沿用这套风格：节点样式只用 backend（白底 ink 描边）/ input（muted 10% 底）/ store（ink 5% 底）/ external（ink 3% 底）/ optional（虚线）/ focal（accent-tint 底 + accent 描边）；连线一律直角，快路径用 link `#2e5aa8`，慢路径/焦点用 accent 虚线，控制面用 muted 虚线；每张图最多两处 accent，图例放底部横条；中文字号 ≥12px，节点 13–14px。示例脚本是 `scripts/make_dd_example.py`（《看懂 DPU》的五张图）：复制到 `<topic>/figs/dd/make_dd.py`，保留 Svg 类、节点样式表和图例函数，只改画图函数；导出用同一个 `scripts/export_cover.py`（非封面画布自动按 2x 导出）。

## 11. 宣传简介（正文之外单独一份）

文档写完后，另写 `<主题>_宣传简介.md`，用于发布时放在文档旁边（公众号/知乎/小红书的导语、资料包说明）。它不进正文。样板：`assets/blurb-example.md`（《看懂 DPU》的简介，用户亲手改过，以它的语气为准）。结构：

```
# 《<文档标题>》简介

![](figs/cover/cover.png)

可以了解到：

1. <最核心的那个"为什么"，用大白话讲清因果，例："DPU 兴起的两个原因：网卡带宽和 CPU 增速之间的差距越拉越大，CPU 跟不上高速 I/O；云上的 CPU 是租给客户赚钱的，而网络、存储、安全这些公共设施会占掉可以出租的 CPU。这三者也是 DPU 的核心功能。">

2. <一组对照/比较，例："内核协议栈、DPDK、XDP、卸载网卡四种网络栈的对照。">

3. <历史脉络，例："I/O 卸载的历史：从 1958 年的通道处理器讲到今天的 DPU。">

4. <内部结构 / 代表产品，例："DPU 内部结构、软件栈，以及当前最有竞争力的产品分析。">

**适合：** <1 句话，具体到人群和所需背景>
```

- **大白话**：像跟朋友介绍一样说"能了解到什么"，不用"读完你能……""一张总览图把 X 放进同一平面"这类书面腔和内部术语（坐标轴、母题、焦点圈等写作行话不出现）。
- 只写一个"可以了解到"编号列表，3–5 条，每条对应正文的一块内容；第 1 条放最核心的"为什么"，可以写两三句把因果讲透，其余每条一句话。
- 不单列"包含什么"、不写页数/图数/参考文献数等统计信息，不写开头钩子段。
- **全文不超过 500 字**（不含图片和标题）；只写正文里真有的内容，数字与正文一致，不夸大。
- 同样遵守隐私边界：不出现用户本人的研究、项目、单位。
- 不需要 PDF。
